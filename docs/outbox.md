# Контракт Outbox Event

Это публичный контракт ядра: потребитель получает события в таком виде и может на него
рассчитывать. Всё остальное внутри ядра может меняться.

## Поля события

| Поле | Тип | Смысл |
|---|---|---|
| `event_id` | UUID | Идентификатор события. По нему потребитель отбрасывает дубликаты. |
| `sequence` | целое, монотонно растёт | Порядковый номер события в outbox. По нему потребитель упорядочивает события. |
| `type` | строка | Вид факта, например `transaction.posted`. |
| `payload` | JSON-объект | Данные факта; состав зависит от `type`. |
| `occurred_at` | дата и время (UTC) | Когда событие записано, то есть когда факт попал в базу. |

Событие сообщает, что произошло, и никогда не просит что-то сделать.

### `transaction.posted`

```json
{
  "transaction_id": 42,
  "kind": "transfer",
  "reversal_of": null,
  "posted_at": "2026-10-18T12:00:00+00:00",
  "entries": [{"account_id": 1, "amount": -100}, {"account_id": 2, "amount": 100}]
}
```

`amount` в минорных единицах валюты, со знаком (ADR-0001).

### События холдов

Поля общие для всех трёх: `hold_id`, `account_id`, `amount` (сумма холда, минорные единицы),
`status` (`active`, `captured`, `released` или `expired`: статус после события) и `expires_at`
(ISO 8601, UTC).

### `hold.placed`

Холд поставлен, его `status` — `active`.

```json
{
  "hold_id": 7,
  "account_id": 1,
  "amount": 300,
  "status": "active",
  "expires_at": "2026-10-18T12:15:00+00:00"
}
```

### `hold.captured`

Холд списан полностью или частично. `captured_amount` — списанная сумма (не больше `amount`),
`transaction_id` — проведённая транзакция списания (на неё же ушло `transaction.posted`).
Остаток `amount - captured_amount` снова доступен.

```json
{
  "hold_id": 7,
  "account_id": 1,
  "amount": 300,
  "status": "captured",
  "expires_at": "2026-10-18T12:15:00+00:00",
  "captured_amount": 200,
  "transaction_id": 43
}
```

### `hold.released`

Холд закрыт без списания. `reason`: `released` (снят вызовом API) или `expired` (истёк срок);
`status` совпадает с `reason`.

```json
{
  "hold_id": 7,
  "account_id": 1,
  "amount": 300,
  "status": "expired",
  "expires_at": "2026-10-18T12:15:00+00:00",
  "reason": "expired"
}
```

## Гарантии

- **Событие есть тогда и только тогда, когда есть факт.** Событие пишется в той же транзакции БД,
  что и проводка. Откат проводки откатывает и событие.
- **At-least-once.** Relay доставляет событие, затем помечает его `delivered_at`. Если relay упал
  между этими шагами, событие уйдёт повторно (с тем же `event_id` и `sequence`). Потребитель
  обязан быть идемпотентным по `event_id`.
- **Порядок по `sequence`.** Потребитель получает события строго по возрастанию `sequence`, в том
  числе между пачками и после сбоев: недоставленная пачка уходит заново раньше всего, что за ней.
  Это держится на двух вещах (ADR-0012). Писатель берёт транзакционную advisory-блокировку перед
  вставкой события и держит её до коммита, поэтому порядок коммитов совпадает с порядком
  `sequence`, и событие с большим `sequence` не становится видимым раньше меньшего. Relay
  выполняет один проход за раз; второй одновременный проход ничего не доставляет. Пропуски в
  `sequence` возможны (откат транзакции расходует номер), монотонность они не нарушают.
- **Цена порядка.** Запись событий сериализована: транзакции, пишущие в outbox, выстраиваются в
  очередь от вставки события до коммита. Событие пишется последним шагом транзакции, так что под
  блокировкой остаются только вставка и коммит; пропускная способность записи ограничена
  скоростью коммитов Postgres (порядка тысяч в секунду на обычном диске), а не числом воркеров.
  Один «ядовитый» потребитель задерживает все события за ним.

## Как работает relay

Задача `django.tasks` `ledger.outbox.tasks.relay_outbox` за один проход:

1. В транзакции берёт advisory-блокировку relay (занята — проход пустой) и до 100
   недоставленных событий по `sequence`.
2. Вызывает потребителя для каждого события.
3. Ставит `delivered_at` и коммитит.
4. Ставит в очередь следующий проход через `OUTBOX_RELAY_INTERVAL_SECONDS` (по умолчанию 5).
   Исключение потребителя не обрывает цепочку: следующий проход ставится, и пачка уходит заново.

Цепочка проходов одна. Её ведёт строка `TaskChain` с токеном и арендой (`lease_until`): каждый
проход продлевает аренду, ставя следующий. `python manage.py start_outbox_relay` запускает цепочку,
только если живой нет, поэтому его можно вызывать сколько угодно раз и из cron. Если воркер убит
посреди прохода, следующий проход не поставлен; через `OUTBOX_RELAY_INTERVAL_SECONDS +
TASK_CHAIN_GRACE_SECONDS` (по умолчанию 5 + 60 секунд) аренда истекает, и очередной вызов
`start_outbox_relay` (или планировщика) заводит цепочку с новым токеном. Задача со старым токеном
ничего не доставляет и не перепланируется. Проход должен укладываться в
`TASK_CHAIN_GRACE_SECONDS`. Выполняет задачи воркер `python manage.py db_worker` (ADR-0005).

## Демо-потребитель

`ledger.outbox.consumer.record_delivery` пишет событие в `DeliveredEvent` через собственное
соединение с БД и коммитит сразу, как внешняя система: падение relay до `delivered_at` не
откатывает запись потребителя, и повторная доставка действительно приходит к нему дублем.
Уникальность по `event_id` отбрасывает дубликат. Любому настоящему потребителю дедупликация по
`event_id` нужна обязательно.
