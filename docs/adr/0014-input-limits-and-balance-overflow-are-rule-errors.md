# Крайние значения на входе дают 4xx, переполнение баланса это ошибка правила

Posted Balance хранится в bigint (ADR-0001), поэтому любое значение, которое можно прислать, должно либо
помещаться, либо отклоняться с кодом, а не падать в 500 на INSERT или UPDATE. Лимиты лежат в
`ledger/limits.py`:

- Amount проводки, холда и capture: абсолютное значение не больше `MAX_AMOUNT = 10**18` (меньше
  `2**63`, чтобы запас оставался на накопление). Схема `Amount` даёт 422 валидации ninja; сервис
  повторяет проверку для вызовов в обход API (`amount_out_of_range`). Отрицание записи при reversal
  больше не может выйти за int64.
- Накопление: если Posted Balance после проводки вышел бы за bigint, posting engine до записи
  бросает `balance_overflow` (422), баланс и снапшот не меняются.
- `ttl_seconds` холда: не больше `MAX_TTL_SECONDS` (один год), иначе `now + ttl` переполняет datetime.
  422 валидации.
- Idempotency-Key и X-Source-System: не длиннее 255 символов (размер колонок). Проверка в
  `MutationHeaders` до заявки, ответ 400 `header_too_long`, как у `missing_header`.

Границы включительные: ровно максимум проходит. Ошибка правила (`balance_overflow`) сохраняется и
воспроизводится идемпотентно как любая другая (ADR-0009); отказ на входе до заявки ничего не хранит.

Лимит `10**18` (10**16 единиц основной валюты при двух знаках) заведомо выше любой реальной суммы; его можно поднять до `2**63 - 1` без миграций.
