# Доказательства конкурентности: отдельный маркер, общий проверяльщик инвариантов, контрольный дедлок

Гарантии «не задвоится, не уйдёт в минус, без дедлоков» нельзя проверить последовательным тестом.
Поэтому они доказываются многопоточными тестами против настоящего Postgres (`tests/test_concurrency.py`,
маркер `concurrency`). Тесты идут в posting engine и сервисы напрямую, не через HTTP: упираться должна
база, а не сервер; исключение один тест идемпотентных повторов, он идёт через HTTP-клиент, потому что
идемпотентность живёт на границе API.

Решения, которые можно было принять иначе:

- **Инварианты в продуктовом коде.** `ledger/invariants.py` (`check_invariants`, `assert_invariants`)
  проверяет: сумма Posted по всем счетам равна нулю, Available счетов asset и liability не
  отрицателен, каждый снапшот равен пересчёту Entry. Проверка в `src`, а не в `tests`, потому что её же
  вызывает нагрузочный генератор. Вызывать её нужно, когда писатели закончили.
- **Порядок блокировок наблюдаем.** Posting engine берёт блокировки по одной строке
  (`_lock_account`) в порядке `_lock_order` (по возрастанию id, без повторов). Раньше один
  `select_for_update ... id__in` отдавал строки в порядке индекса независимо от нашей сортировки, и
  тест встречных переводов проходил даже при развёрнутом порядке. Теперь порядок задан кодом движка.
- **Контроль дедлока на одной нагрузке.** Один тест гоняет встречные переводы a->b и b->a через
  настоящий `post_transaction` дважды. Подмена `_lock_account` держит каждую транзакцию после первой
  блокировки на `threading.Barrier`. Упорядоченный движок: пара застревает за первой блокировкой,
  барьер по таймауту отпускает, дедлока нет. Мутант `_lock_order` (порядок как в строках запроса):
  обе транзакции держат по строке и ждут друг друга, ровно одна жертва получает `DeadlockDetected`.
  Отдельный тест проверяет сам порядок: перевод по четырём счетам в перемешанном порядке строк
  блокирует их строго по возрастанию id. Разворот порядка (`reverse=True`) сам по себе дедлока не даёт, его ловит
  проверка порядка.
- **Мутационная проверка.** Вручную правился `_lock_order` в `ledger/posting/service.py`: (1) порядок
  как пришёл (`list(dict.fromkeys(ids))`): падают четыре теста (встречные переводы, контроль дедлока, порядок); (2) убывающий порядок
  (`sorted(..., reverse=True)`): падают контроль и тест порядка. Без правок оба проходят.
- **Нагрузка через env.** `LEDGER_CONCURRENCY_THREADS`, `_OPS`, `_ACCOUNTS`, `_ROUNDS`, `_REPEATERS` с
  малыми значениями по умолчанию, чтобы CI укладывался в секунды; локально их можно поднять. У каждой
  переменной есть нижняя граница (потоки и повторители не меньше 2, счета не меньше 2, остальные не
  меньше 1); нечисло или значение ниже границы даёт `ConcurrencyConfigError` с именем переменной при
  импорте, а не падение посреди теста.
- **Маркер зарегистрирован, в CI отдельный шаг.** `pytest -m "not concurrency"` и `pytest -m concurrency`
  идут раздельными шагами, чтобы падение конкурентности было видно сразу. Обычный `pytest` запускает
  всё.

## Consequences

- Тесты используют `django_db(transaction=True)`: каждый поток видит закоммиченные данные своим
  соединением, таблицы очищаются после теста.
- Мутантный прогон ждёт `deadlock_timeout` Postgres (1 с по умолчанию), упорядоченный до 1,5 с барьера.
