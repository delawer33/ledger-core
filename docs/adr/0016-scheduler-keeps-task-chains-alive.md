# Планировщик не ставит задачи по таймеру, он держит живыми цепочки

Истечение холдов, сверка и relay должны идти без ручных команд и внешнего cron, а `django.tasks`
с бэкендом `django-tasks-db` (ADR-0005) периодики не умеет. Раньше `expire_holds` и
`reconcile_task` никто не запускал, поэтому холды не истекали.

## Решение

Каждая периодическая задача это Task Chain (ADR-0012): проход делает работу и сам ставит
следующий через `run_after`. Холды и сверка получили тот же механизм, что у relay
(`ledger/chains/service.py`), второго не появилось. Планировщик, команда `run_scheduler`, лишь
в цикле зовёт `ensure_chain` для каждой цепочки из реестра `ledger/scheduler.py:SCHEDULED`.
`ensure_chain` под блокировкой строки заводит цепочку, только если её нет или аренда истекла.
Поэтому:

- перезапуск планировщика и два экземпляра, работающие одновременно, не ставят задачу дважды:
  второй вызов видит живую аренду и ничего не делает;
- цепочка, у которой убили воркер, поднимается планировщиком после истечения аренды, тем же вызовом
  (для relay это Task Chain из ADR-0012, теперь без ручного `start_outbox_relay`);
- без планировщика уже запущенные цепочки продолжают идти, он нужен для старта и восстановления.

Задачи `expire_holds` и `reconcile_task` без токена по-прежнему работают как разовый запуск
(`reconcile --enqueue`, тесты, ручной вызов); с токеном это проход цепочки. Ошибка прохода не
обрывает цепочку: следующий проход ставится в любом случае.

Рассматривали цикл, который ставит задачи по таймеру с дедупликацией по слоту времени. Отказались:
нужен второй механизм «один раз за интервал», а recovery после падения воркера всё равно требует
аренды.

## Настройка

Интервалы в секундах из env: `HOLD_EXPIRY_INTERVAL_SECONDS` (30), `RECONCILIATION_INTERVAL_SECONDS`
(3600), `OUTBOX_RELAY_INTERVAL_SECONDS` (5); `SCHEDULER_POLL_SECONDS` (15) задаёт, как часто
планировщик проверяет цепочки. Compose поднимает `worker` (`db_worker`) и `scheduler`
(`run_scheduler`) рядом с `api`, оба с `restart: unless-stopped` и healthcheck: у воркера это
проверка доступа к БД, у планировщика файл-heartbeat, который цикл обновляет после каждого прохода.

## Consequences

- Интервал цепочки не точен: следующий проход ставится после конца текущего, период равен
  интервалу плюс длительность прохода и задержка очереди.
- Проход обязан укладываться в `TASK_CHAIN_GRACE_SECONDS` (ADR-0012), иначе цепочку заведут заново;
  старая выйдет по токену. Для сверки большой базы grace надо увеличить.
- Истечение холдов запаздывает не больше чем на интервал плюс grace при падении воркера.
- Новую периодическую задачу добавляют как цепочку и регистрируют в `SCHEDULED`.
