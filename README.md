# Ledger Core

Ядро учёта денег маркетплейса на двойной записи: деньги продавцов, комиссия платформы, холды под
возвраты, выплаты на банк. Внешние системы ходят в него по HTTP. Любая операция — Transaction из
Entry с нулевой суммой, поэтому деньги не появляются и не исчезают, а только переходят между счетами.

Глоссарий: [CONTEXT.md](CONTEXT.md). Решения: [docs/adr](docs/adr). Спецификация: [docs/PRD.md](docs/PRD.md).
Команды и раскладка: [CLAUDE.md](CLAUDE.md). Контракт событий: [docs/outbox.md](docs/outbox.md).

## Что гарантируется и чем доказано

Все тесты идут против настоящего Postgres 17, без моков базы.

| Гарантия | Где держится | Доказательство |
|---|---|---|
| Сумма Entry транзакции равна нулю, Entry нельзя изменить или удалить | триггеры Postgres (ADR-0004) | `tests/test_db_guards.py` |
| Повтор запроса с тем же Idempotency-Key возвращает первый ответ байт в байт и не проводит второй раз, в том числе при параллельных повторах | запись-заявка и сохранённый ответ (ADR-0009) | `tests/test_idempotency.py`, конкурентный набор |
| Встречные переводы не дедлочатся | блокировка счетов по одному в порядке id (ADR-0013) | `tests/test_concurrency.py`: контрольный тест показывает, что без упорядочивания та же нагрузка дедлочится |
| Счёт продавца не уходит в минус, холды учитываются | проверка Available под блокировкой счёта | `tests/test_concurrency.py`, `tests/test_holds_api.py` |
| Событие о проводке не теряется и доставляется по порядку, дубли отбрасываются | outbox в той же транзакции, relay с lease (ADR-0012) | `tests/test_outbox_relay.py`, `tests/test_outbox_order.py` |
| Разошедшийся снапшот не чинится молча: открывается Incident, баланс считается по Entry, доверие возвращает только человек | сверка (ADR-0003, ADR-0015, ADR-0017) | `tests/test_reconciliation.py` |
| Холды истекают, сверка и доставка идут без ручных команд | планировщик на `django.tasks` (ADR-0016) | `tests/test_scheduler.py` |

Конкурентный набор: `uv run pytest -m concurrency`. CI на каждый push: gitleaks, ruff, mypy strict, pytest
(обычный и конкурентный прогоны), deptry, сборка образа.

## Нагрузка

Генератор (`manage.py loadgen`, ADR-0019) ходит по HTTP в запущенный стек и в конце каждого прогона
проверяет инварианты той же функцией, что конкурентные тесты: сумма Posted равна нулю, Available не
отрицателен, снапшоты равны пересчёту. Повторы сверяются с первым ответом байт в байт. Прогон с
нарушенным инвариантом или расхождением повтора помечается FAILED и сюда не попадает.

Сценарии: `random` — переводы между 20 счетами; `hot` — встречные переводы между двумя счетами;
`mixed` — переводы, холды с capture и release, повторы с теми же ключами. Комиссии и выплаты
под нагрузку пока не входят: это те же проводки движка, но отдельно они не измерялись.
Каждый прогон 60 с, git `3cfbcfa`. Сырые отчёты: [docs/load](docs/load).

| Машина | Профиль | Сценарий | ops/s | p50, мс | p99, мс | Ошибки | Дедлоки | Инварианты |
|---|---|---|---|---|---|---|---|---|
| VPS, AMD EPYC-Rome, 2 vCPU, 3.8 GB | lab, 8 клиентов | random | 8.9 | 890 | 1816 | 0 | 0 | OK |
| | | hot | 9.6 | 788 | 1516 | 0 | 0 | OK |
| | | mixed | 11.9 | 641 | 1463 | 0 | 0 | OK |
| Ноутбук, i5-12500H, 16 потоков, 15 GB | lab, 8 клиентов | random | 9.2 | 802 | 2003 | 0 | 0 | OK |
| | | hot | 11.7 | 682 | 1393 | 0 | 0 | OK |
| | | mixed | 11.0 | 684 | 1904 | 0 | 0 | OK |
| Ноутбук, i5-12500H, 16 потоков, 15 GB | large, 16 клиентов | random | 67.9 | 192 | 808 | 0 | 0 | OK |
| | | hot | 54.5 | 269 | 576 | 0 | 0 | OK |
| | | mixed | 82.5 | 169 | 593 | 0 | 0 | OK |

Лимиты контейнеров:
- **lab** (одинаковый на обеих машинах, влезает в бюджет песочницы VPS): api 0.3 CPU / 384 MB
  (gunicorn 2×4), db 0.25 CPU / 448 MB, worker 0.1 CPU, scheduler 0.05 CPU, генератор 0.1 CPU.
- **large**: api 2 CPU / 1 GB (gunicorn 4×4), db 2 CPU / 2 GB, worker и scheduler по 0.5 CPU,
  генератор 1 CPU.

Что из этого следует. Цифры показывают поведение под нагрузкой с проверкой корректности, а не
предел пропускной способности. Узкое место — сам сервис: в профиле large api упирается в свои 2 CPU,
Postgres занимает около 1.8 CPU, генератор около 5%. Каждая проводка — это заявка идемпотентности,
блокировки счетов, обновление снапшотов и запись в outbox под advisory-блокировкой, которая
сериализует запись событий ради строгого порядка (ADR-0012). На профиле lab VPS и ноутбук дают
одинаковые цифры, потому что упираются в одни и те же лимиты. Главное, что держится на обеих
машинах: ноль дедлоков в `hot`, ноль ошибок, инварианты сходятся.

Воспроизвести (порты хоста задаются в `.env`):

```bash
docker compose -p ledger-load -f docker-compose.yml -f docker-compose.load.yml up -d --build
DATABASE_URL=postgres://<user>:<password>@127.0.0.1:<DB_PORT_EXTERNAL>/<db> \
  uv run python manage.py loadgen run --scenario hot --base-url http://127.0.0.1:<API_PORT_EXTERNAL>/api/v1 \
  --workers 16 --duration 60 --accounts 2 --seed 1 --output docs/load/my-hot.json
uv run python manage.py loadgen table docs/load/*.json
docker compose -p ledger-load stop
```

Лимиты меняются через env `LOAD_API_CPUS`, `LOAD_DB_CPUS`, `GUNICORN_WORKERS` и другие
(см. `docker-compose.load.yml`).

## Запустить

```bash
cp .env.example .env    # задать порты, пароль БД и DJANGO_SUPERUSER_*, если нужна админка
docker compose up --build
```

Swagger: `http://127.0.0.1:<API_PORT_EXTERNAL>/api/v1/docs`, админка только для чтения: `/admin/`.

Проверки как в CI (нужен `DATABASE_URL` на любой Postgres 17, кроме порта 5432):

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest && uv run deptry src
```
